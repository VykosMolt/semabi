## Order before learning

1. Root adopts a concrete source/configuration freeze, verifies the source
   hashes, finishes prior owned jobs, and coordinates the reserved installation.
   The independent evaluator waits for the accepted freeze and startup receipts.
2. The evaluator may then initialize the account and inspect ordinary rendered
   UI. Charge account provisioning, authentication, failed attempts, navigations,
   reloads, fixture construction, changed fixtures, and challenge preconditions
   to one cumulative setup allowance: 900 seconds, 60 interactions, and 20
   possible writes. A new browser, reset, or setup phase does not renew it.
   Record opaque installer work and process cost separately.
3. Choose the normal record concept and usable fields from that UI. Record the
   UI opportunity for each family, including missing or inaccessible features.
   Use ordinary user-visible values; create no task yet from a learned schema.
   Do not inspect application source, databases, hidden endpoint responses,
   private client stores, or native object identifiers to infer operations.
4. Construct the smallest useful shared fixture that supports the predefined
   families. Use fresh run-specific textual tokens, at least two distinguishable
   records, a deliberate shared-label collision, and one unrelated record whose
   change can test selection stability where the UI permits these states.
   Use a visible category/tag/project only if the UI actually exposes it.
   Preserve required but unavailable fixture states as unestablished.
5. Before either arm learns, freeze the concrete ordered goals, supplied
   arguments, initial/changed fixture descriptions, target and sampled
   non-target observations, expected visible results, applicable scopes, and
   challenge preconditions in evaluator-only files. Decide the relationship
   substitution at this point, using the evidence described below. Fix case IDs,
   denominator, and arm order before any learner or baseline performance.
6. Root records the equivalent fixture/reset mechanism and exact lifecycle
   implementation before concrete-task adoption and assessment. It copies data
   opaquely and supplies no operation knowledge. Check the relevant visible
   fixture state independently after restoration. Account/fixture preparation
   is separate from connection and onboarding.
7. Connect and onboard once through the public SemABI HTTP entry point, using
   only the authorized origin, credentials, and generic exploration settings.
   Deduct connection navigation and authentication from the shared onboarding
   allowance before learning. Preserve every failed exploration and its costs.
   Freeze the resulting public operation catalog and shared binding receipts.
   Both arms receive the same automatically learned artifact. Charge its
   acquisition expense to both comparison arms; count physical acquisition once.

An access failure or missing UI remains explicit. An access failure may support
a separately recorded application replacement before onboarding; a performance
failure may not remove the application or requests. Exhausting setup creates an
incomplete fixture result with all requested cases retained. Do not repair a
checker by consulting private application state, silently replenish the setup
allowance, or choose easier goals after a binding rejection.

## Core request construction

Use this order: R1, R2, C1, C2, U1, U2, D1, D2, M1, M2. The table gives templates;
the evaluator must instantiate them from ordinary UI before onboarding.
A missing opportunity or unsupported goal remains a scored request.
Primary and secondary fields are selected from the observed UI, independently
of the learner's operation schema or the binder's restricted grammar.

| Family | First request | Second request | Independent result required |
| --- | --- | --- | --- |
| R: find/read | Find one prepared record by a fresh visible text token. | Find the intended record after unrelated account contents change. | Structured selected content and the relevant visible fields within a stated search scope. |
| C: create | Create a record with the supplied content and ordinary requested attributes supported by the UI. | Create another record with different fresh values after service restart and in a fresh browser session. | Exactly one intended record within the checked scope, with every requested value retained after reload. |
| U: update | Change specified content of a uniquely described existing record, retaining its identifying context and unrequested fields. | Update a specified record after another record changes; use a second ordinary editable property or state if the UI exposes one. | The requested target state, retained identity/context, and unchanged sampled non-target records. |
| D: distinguish duplicates | Select one of two records sharing a requested label/fragment using an additional visible qualifier. | Select the intended record using a different secondary qualifier. | Only the fully specified target is returned or affected; both colliding records are independently checked. |
| M: multiple steps | Create a record with an exposed visible classification and find it through that classification. | Find another classified record, update its content or state, and read it back. | Every required selection and the final state are independently checked. |

Do not infer tags, projects, status controls, or relationships from the
application name. Where there is only one visible content field, an ordinary
full-content replacement can instantiate U. Where multiple fields or state
choices are requested, retain those clauses even if the frozen binder cannot
dispatch them. Do not add defaults, remove attributes, pre-read and merge
values, or split a goal into evaluator-supplied operation calls.

For paired cases, give both arms identical goals and argument values from an
equivalent restored state. Fresh values differ between cases; restoring the
fixture permits the same fresh values in both arms of a pair. Prepare a base
fixture and any necessary changed variants through ordinary UI, charging their
cumulative setup costs. The second R/U requests must preserve their intended
target while changing another relevant record. Keep learner artifacts outside
application fixture restoration.

## Optional relationship block

Replace M1 and M2 with REL0, REL1, RELM, and RELA only if ordinary UI establishes
an actual relationship before onboarding. Retain evidence of the relation and
the direction/projection requested; adjacent text, a shared tag, filtering, or
co-occurrence alone does not establish a learned relationship.

Construct four cases in this fixed order:

1. REL0: no witnesses under the requested relationship and stated scope.
2. REL1: one witness with one projected answer.
3. RELM: multiple witnesses with distinct projected answers.
4. RELA: multiple witnesses agreeing on the same projected answer.

Record the substitution, its rationale, and concrete fixtures before learning.
The result has 12 core and 18 total requests per arm. Without established UI
relationships, retain M1/M2 and report relational coverage unestablished.
Constructing this block does not itself establish learned JOIN or witness
induction.

## Six challenges, in fixed order

1. CH1: read an absent value and require an accurate empty result under a
   stated, independently checked search scope.
2. CH2: request an update using only a deliberately duplicated label. Check
   both records; a safe ambiguity response is accurate abstention, not a
   completed state change.
3. CH3: repeat a positive request at a different evaluated viewport with fresh
   values and the same semantics. Record the actual presentation difference.
   This frozen HTTP harness has no evaluated viewport intervention, so retain
   the goal with intervention unavailable. The setup viewport is not evidence
   that the evaluated request ran at a different viewport.
4. CH4: change or remove a target/precondition through ordinary UI before
   invoking the saved operation. Require reconciliation, explicit staleness or
   withdrawal, or justified success under the still-valid meaning. Silent
   retargeting fails. Charge preparation of this state to the setup ledger.
5. CH5: end the evaluated session through normal logout, then request a
   positive operation. Charge reauthentication or record explicit
   `AUTH_REQUIRED`. This harness has no owned-session logout intervention;
   retain the goal as unavailable, without fabricating client state.
6. CH6: interrupt only the owned evaluated browser after its first recorded
   write intent and before confirmation. Read back independently before any
   retry, recording zero, one, multiple, or unestablished effects and recovery
   cost. This harness has no suitable browser intervention point; retain that
   limitation. An external process meter is not this intervention.

The challenge limitations are frozen from the common harness before reserved
UI access. There is no new harness intervention or task substitution in this
candidate.

## Shared binding and execution

Use the exact [shared binding policy](../product_assessment_development_v1/binding/policy.md)
and binder source identified in the JSON. Its limited complete-goal grammar
supports qualifying single-field creation and exact sole-value replacement.
Its inputs are only the ordinary goal, its arguments, and the learned public
operations for the current connection. Application names, case IDs, expected
answers, selectors, mappings, traversal recipes, and manual demonstrations are
not binder or learner inputs. Schema bindings are produced automatically.
A unique complete bijection is required, with no defaults, conversions, implicit
read/merge/update chain, clause omission, or manual rescue of rejected requests.

Both arms receive the identical eligible call and learned artifact. Ineligible
requests stay in the denominator as unsupported. Eligibility means no browser
execution; general goal planning remains unestablished. The baseline's
`DISPATCHED` is only dispatch evidence and requires the same independent effect
check as a SemABI result.

Root will use byte-identical copies of `invoke_http.py`,
`run_service_call.py`, and `run_baseline_call.py`, plus the ten-file
`source_sha256.json`, in `runs/product_assessment_reserved_v1/`.
Their directory depth is unchanged; `run_service_call.py` resolves its
`BASE` to that directory and therefore uses
`runs/product_assessment_reserved_v1/service/`.
The fixed service address is `http://127.0.0.1:8860`, serialized after the
development service and jobs finish. Credentials and service tokens remain in
private files and are never copied into goals or expected-result publications.
The existing binder and external command meter are shared by their frozen
paths/hashes. No changes to learner, baseline, binder, or caller logic are
authorized by this candidate.

Run paired arms sequentially. For odd-numbered cases run SemABI first; for
even-numbered cases run cached_form first. Number cases once in the frozen
ordered list, including any four-case relationship substitution. Restore and
independently check equivalent fixtures before each arm, keeping preceding
evidence. Without equivalence, label the case unmatched and exclude it from
paired-comparison pooling while retaining its task outcome.

Every accepted HTTP job must reach a known terminal state before restoration
or another arm. A lost invocation reply requires retained idempotency identity
and reconciliation/read-back; timeout is not cancellation. A result arriving
after the workflow deadline does not become an on-time completion. Record
service startup, reconciliation, shutdown, resets, and other assistance
separately as well as in the complete cost account.

## Fixed limits and result accounting

| Phase | Wall seconds | Interactions | Possible writes |
| --- | ---: | ---: | ---: |
| Cumulative evaluator account/fixture setup | 900 | 60 | 20 |
| Connection and onboarding, including authentication | 900 | 120 | 40 |
| Each requested workflow, including navigation/authentication | 60 | 20 | 12 |
| Independent verification per request | 30 | 12 | 8 search/filter actions; no saved business changes |
| CH6 recovery, only after justified read-back | 60 additional | 10 | 2 |

Keep aggregate heavy-job allocation within 12 cores, each evaluated browser
worker within two cores, numerical libraries at one thread, and stop an
evaluation worker exceeding 4 GiB RSS. The inherited worker affinity is
`[2, 3]`; set thread environment values to one at launch. No paid resources or
runtime model calls are budgeted. Evaluated viewport is 1400 by 1000; fixture
viewport is 1280 by 900. Reauthentication, typing, selections, checking, clicks,
failed actions, navigation, and reloads all count. Count polling/snapshot reads
separately and include their wall time. Raw internal snapshot counts are not
exposed by this service and remain unmeasured; public observation events are a
different reported quantity. Report external wall time, CPU, sampled peak RSS,
retries, restarts, resets, manual minutes/actions, and any app-specific code.
Record the caller's budget decision and the external timing evidence; preserve
late or unfinished jobs and any accounting gap explicitly.

There are ten core plus six challenge requests: 16 requests and 32 arm-result
slots for one application. With the prior relationship substitution there are
12 core plus six challenges: 18 requests and 36 arm-result slots. Preserve
unsupported, refused, inaccessible, failed, incomplete, and unconfirmed cases.
Report independently completed workflows over all predefined requests and core
completion separately, by family and arm. Report independently correct
observable outcomes over actual invocations, with invocation coverage,
`CONFIRMED` precision, false confirmations, and wrong side effects separately.
Zero invocations means undefined invocation correctness. Repeated snapshots do
not add tasks; accurate abstention does not complete a requested write.

The unchanged milestone criterion is at least 8/10 core tasks on each
application, a success in every core family, fresh-session and service-restart
reuse, zero independently detected wrong side effects, and zero false
confirmations. If the relationship block is chosen, require 9/12 core and
correct multiplicity in all four relationship cases. These are bounded
demonstration criteria. Neither this candidate nor a successful isolated call
establishes the milestone.

Any learner/baseline/policy repair after first reserved access ends that fixed
assessment and moves the application into development. Preserve the first
result unchanged; a repaired run is not untouched transfer.
